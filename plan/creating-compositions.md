The herd app would allow for the creation of Compositions (see [[composable-structure]]).
The user interface would be pretty influenced by Elektron sequencer devices, although adjusted for a Web App interface style.

You would be able to add a Program to the composition to then add 1 to 4 voices to that program. Within a Voice, the UI will start to look like familiar electronic music devices. Each voice has one Pattern device, one Instrument device, one Visualizer device, and one UI device. A Pattern device is a sequencer like a step sequence or Euclidean generator. A step sequencer should have a configurable number of steps up to 64. An Instrument is a sampler or a polyphonic SH-101-style synth.

A step on the sequencer with authored data should be called a Step Event. A Step Event can contain an Instrument Trigger, a Visualizer Trigger, both, or neither. The Instrument Trigger sends an Instrument Sounding Event, roughly equivalent to MIDI Note On. The Visualizer Trigger sends a Visualizer Display Event, the visual equivalent of Note On. The Instrument and Visualizer define default values, while Step Event Parameter Locks override those defaults for a single event. For example, one Step Event might trigger a note with locked pitch and velocity, another might trigger only a visual Cel with locked shape and saturation, and another might only lock filter cutoff without triggering either a note or a visual event.

A Visualizer would look like an electronic music device and would take note-like input and create simple visuals like a wash of color, so the device would have parameters that affect how HSBA color and shape are chosen, how this evolves per Cel (a single visualizer event) and throughout a Pattern, Program, Composition, etc.

A UI device would allow you to create prompts and choices that feed back in to the composition. An example you would be able to say after this pattern has been going on for eight loops than this text would appear, and once cycle after that, these two buttons would appear. And we wouldn't need to be able to define what those buttons do they would affect the composition they might determine which voice is assigned to the current user. They might set another parameter, which then is used as a modifier on a Step Event.

One simple implementation of this is that every one of these buttons could in the background set a parameter, and then that parameter can be used to modify settings on all the devices. Such as our example of allowing the user to choose which voice they are part of. If they press the button one that could have a setting of +0 on the parameter, whatever is called parameter a. Then in our program interface we could have setting to say "assign user to voice:" with a drop-down that allows, you to choose one of the voices that are present, but next to that is a modifier, and you choose, which parameter is modifying it and there you could choose parameter a. So parameter a started out at zero that person would be in voice 1 and if they pressed the first button which has a value of +0 they would remain invoice one. However, if they press the second button which has a value of plus one then they would end up in voice two. 

What I'm describing here is a modulation layer and it probably is best implemented in the manner that bitwig uses. This would mean having a modulation mode button, which would change the user interface of all devices and overlay each modulatable element with selection of modulation source and amount.

For Step Event Parameter Locks, there should also be a fast capture mode: select a Step Event, choose to create a new lock, then touch or modify an Instrument or Visualizer control. The system should automatically set that control as the lock target and store the edited value as the locked value for the selected Step Event.
